# Проверка версии 0.3.1 — 6 октября 2026

**169 тестов прошли на Python 3.11 и 3.12.** Добавлена проверка трёх вариантов короткого примечания с датой/временем по Москве без секунд; ID находится только в custom-поле. Полные данные семьи и исходный комментарий сохранены в коммуникации без служебной метки.

Отдельно проверены: сохранение communication ID и списка существовавших комментариев до записи; потерянный ответ и перезапуск без повторной коммуникации; одинаковый старый комментарий не подменяет новую запись; несколько новых точных совпадений приводят к проверке администратора. Незавершённая заявка старого формата сохраняет прежний payload для корректной сверки уже отправленной записи.

Образ `itishkino-promobot:0.3.1-amd64` собран и экспортирован. Ограниченный Docker-запуск без сети (256 МБ / 0,75 CPU / 64 PID, UID 10001, read-only root) доставил две mock-заявки разных филиалов с новым форматом полей, сохранил комментарии, подписки и UI. В рабочей CRM тестовых записей не создавали.

## Автоматические тесты

**162 passed** на Python **3.11** и **3.12**, Linux amd64. Полный набор также прошёл на локальном Python 3.14. Проверены:

- Одновременные анкеты двух промоутеров: одинаковый контакт в разных филиалах создаёт независимые карточки и комментарии в нужных филиалах. Выбор/редактирование филиала одной анкеты не меняет другую; подтверждённые настройки фиксируются в заявке.
- Подписки каждого администратора на филиалы: ошибки идут выбранным получателям. Доступ к другим филиалам сохраняется, общие сбои Telegram/сервиса получают все администраторы.
- Добавление новых администраторов другими администраторами, добавление/редактирование имени промоутера, запрет этих действий обычному пользователю, сохранение ролей/имён после открытия базы заново.
- CSV первоначальных администраторов без отдельного `ADMIN_TELEGRAM_ID`, совместимость со старым JSON и ролью владельца.
- Одно сообщение меню на пользователя, редактирование после ответов текстом и кнопками, сохранение message ID в SQLite, эмодзи/галочки. Неизменённое меню, удалённое сообщение, rate limit и callback ack проверены отдельно.
- Просмотр большой Unicode-анкеты страницами в том же сообщении без потери текста. Устаревшие страницы и чужие/устаревшие кнопки не меняют черновики.
- Обновление runtime-конфигурации с сохранением секретов, ролей и резервных копий; dry-run и отказ при неверном CRM ID; миграция существующей базы версии 4 в 5 с сохранением ролей и отдельной pre-migration backup.
- Существующие сценарии анкеты, дубли/архив, неопределённая запись, повторы, backup/restore, аварии БД, автор коммуникации, начальный этап CRM, сообщения разным чатам и VPN-контейнер.

Обычные тесты используют вымышленные данные и mock HTTP. Отдельный тест проходит через настоящий localhost HTTP-сокет. В реальной CRM этот набор ничего не создаёт.

## Финальный Docker-образ

`itishkino-promobot:0.3.0-amd64` собран для Linux amd64 на Python 3.12; `pip check` не нашёл конфликтов. Базовый образ закреплён digest, зависимости — версиями. Проверены CLI, Compose с VPN и архив `docker save` (~66 МиБ) с SHA256SUMS. Секреты, базы, локальные конфигурации и тестовые зависимости в образ не включаются.

В отдельном синтетическом запуске финальный образ работал от UID/GID 10001 с read-only корнем, без capabilities, без сети, с лимитами **256 МБ / 0,75 CPU / 64 PID**. Два промоутера одновременно заполнили анкеты в Преображенку и Кузьминки; обе доставлены в mock CRM с разными карточками и правильными комментариями. Четыре независимых меню сохранены в SQLite, 28 обновлений выполнены редактированием. Роли/подписки и заявки сохранились после открытия базы заново, backup прошёл проверку целостности. Пиковая RSS Python в этом сценарии — около **173 МиБ**. Это синтетический замер на текущем компьютере, производительность Mac Mini проверяется на месте.

## Рабочая CRM и сеть

Read-only `branch-check` из контейнера подтвердил для четырёх филиалов доступ к API клиентов, воронке (1), источнику (6), `custom_promo_request_id`: Преображенка (4), Кузьминки (3), Марьино (2), Жулебино (1). Контакты и секреты в отчёт не попадают. Новых рабочих карточек и коммуникаций эта проверка не создавала.

Контракт создания реальной карточки ранее проверен в Преображенке: [акт приёмки](crm-acceptance.md). Новые филиалы используют общий контракт; бот после каждой записи проверяет результат и останавливает доставку при расхождении. Первую реальную заявку каждого нового филиала следует дополнительно сверить в интерфейсе CRM.

Владелец подтвердил успешный `network-check` на DietPi через Docker AmneziaWG: CRM и Telegram доступны, webhook отсутствует. Новую версию на сервере ещё нужно загрузить и проверить в Telegram. Локальный рабочий polling остаётся остановленным. Порядок: [обновление 0.3.0](franchise-upgrade.md).

# Производительность — 5 октября 2026

## Замеры на текущем компьютере

SQLite volume расположен на `/dev/sdb2`, ext4, HDD. Исходники и каталог настроек не определяют размещение БД: Docker data-root здесь находится на `/mnt/linux_files/docker_data`.

До оптимизации контейнер в момент замера использовал 0,27% CPU и 121,6 МиБ RAM из лимита 256 МиБ. Это снимок текущей нагрузки, а не максимальная производительность. В очередях не было необработанных событий; отклонённые Telegram-сообщения сохранялись отдельно в `held` и не повторялись бесконечно.

В отдельной синтетической БД на том же volume 40 надёжных транзакций SQLite (`synchronous=FULL`) заняли медианно 33,49 мс, максимум 41,82 мс. Живую базу для измерения не изменяли.

Read-only проверка из контейнера:

- Telegram getMe: 349 мс при первом запросе, затем 59 / 109 / 102 мс.
- CRM login: 358 мс.
- Полный обход 157 карточек CRM: 3128 мс.

Ранее реальные доставки/проверки CRM занимали примерно 7–24 секунды; одна попытка завершилась сетевым timeout примерно через 20 секунд. Текущая сеть могла меняться, поэтому эти значения не доказывают, что причиной был именно VPN.

## Что изменено в 0.2.1

После сохранения Telegram-события обработчик анкеты просыпается по сигналу. После фиксации ответа и новой заявки просыпаются очереди сообщений и CRM. Секундная резервная проверка остаётся для восстановления и внешних административных действий. Периодическая пауза больше не требуется перед обычным ответом.

Три отправителя Telegram могут обслуживать разные чаты одновременно. Claim сообщения атомарен в SQLite; более поздний ответ того же чата не обгоняет pending/processing сообщение. Сетевой запрос выполняется вне блокировки очереди. Медленный чат не блокирует другие чаты. Добавлен частичный индекс для поиска незавершённых сообщений одного чата.

На одну попытку проверки заявки выполняется один свежий полный обход CRM вместо двух: его результат используется для поиска своего request ID и сравнения контактов. Это локальный снимок одной попытки, не долговременный кеш. Следующая заявка получает новый снимок. Чтение созданной карточки и комментария для подтверждения доставки сохранено; старые карточки не изменяются. Окно между поиском дублей и ручным созданием менеджером остаётся, как и раньше.

Логи `telegram_outbox` содержат номер сообщения очереди, тип, результат, возраст в очереди и длительность операции; текст сообщения, Telegram ID и секреты не включаются. Они помогут отличать ожидание очереди от сетевой задержки при дальнейших проверках.

## Сравнение двух образов

Одинаковые HDD/volume, лимиты 256 МиБ и 0,75 CPU, отдельные синтетические базы. Полный Runtime и реальные модели aiogram; Telegram имитируется задержкой 100 мс на API-вызов, внешняя сеть отключена. Для каждого образа — 6 текстовых команд и 6 нажатий кнопки, последовательно. Время измерялось от передачи события polling до ответа имитированного Telegram.

| Сценарий | 0.2.0, медиана / максимум | 0.2.1, медиана / максимум |
| --- | --- | --- |
| Текстовое сообщение | 676 / 1134 мс | 221 / 234 мс |
| Нажатие кнопки | 826 / 867 мс | 377 / 402 мс |

Это небольшой контролируемый тест, не гарантия задержки через реальный VPN и не нагрузочный замер на Mac Mini. Новые регрессионные тесты подтверждают порядок ответов, независимость чатов, пробуждение без потери сигнала и свежесть поиска дублей между заявками. Всего 129 тестов проходят на Python 3.11 и 3.12.

## Для Mac Mini

Размещайте Docker data-root/volume на SSD, а не только исходники. SQLite остаётся с WAL и `synchronous=FULL`: ускорение не получено за счёт ослабления сохранности данных. Ограничения RAM/CPU сохранены. Сетевую задержку и прохождение Docker-трафика через Amnezia нужно измерить на сервере отдельно.

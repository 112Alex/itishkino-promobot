# Обновление до 0.3.1: четыре филиала и новое меню

Меню и вопросы анкеты обновляются в одном сообщении бота. Кнопки имеют эмодзи, выбранные филиалы/мессенджеры отмечаются ✅, добавленные контакты меняют подпись кнопки. Большая анкета открывается страницами в этом же сообщении. Если сообщение удалили, бот создаёт новое меню. Уведомление о результате доставки и ошибки приходят отдельными сообщениями, чтобы их было видно.

В CRM используются филиалы: Преображенка — 4, Кузьминки — 3, Марьино — 2, Жулебино — 1. Для них общий канбан «Основная» (1), начальный этап «Не разобрано» без назначения, источник «Промо со Стивом» (6), технический пользователь (18), поле `custom_promo_request_id`. Проверка 6 октября 2026 подтвердила доступ аккаунта к четырём филиалам, воронке, источнику и полю номера заявки без записи новых карточек. Контракт создания ранее проверен в Преображенке; реальные новые заявки в остальных филиалах нужно проверить в интерфейсе CRM. После каждой записи бот самостоятельно сверяет филиал, контакты, этап, источник и коммуникацию.

## Что получат пользователи

Промоутер выбирает филиал в главном меню или в начале новой анкеты. В проверке заявки **«Исправить → Филиал»** меняет филиал только этой анкеты. У каждого свой черновик и выбранный филиал. Два промоутера могут одновременно заполнять анкеты; очередь CRM доставляет их последовательно, используя отдельные настройки каждой заявки. Это сохраняет защиту от дублей и неопределённого результата записи. Поиск совпадений выполняется в выбранном филиале, включая его архив.

Каждый администратор открывает **«⚙️ Админское меню»**:

- **«👥 Промоутеры»** — добавить по ID/username, задать или изменить имя, отключить доступ. Имена отображаются в списке и кнопках. Ввод имени можно отложить; при отсутствии своего имени используется имя Telegram или username. Числовой ID остаётся в техническом идентификаторе кнопки, но не показывается в обычном списке. При подтверждении приглашения по username ID показывается для проверки аккаунта.
- **«🛡 Администраторы»** — добавить администратора по ID и задать имя. Каждый добавленный администратор также может добавлять других и работает со всеми четырьмя филиалами.
- **«🔔 Мои филиалы для уведомлений»** — отметить филиалы. Выбор сразу сохраняется в базе и переживает перезапуск. Ошибки/совпадения заявок и ошибки отправки сообщений по конкретному филиалу идут подписанным администраторам. По умолчанию выбраны все филиалы. Если выключить все, уведомления по заявкам не приходят. Общие сбои сервиса или Telegram получают все администраторы, поскольку они затрагивают весь бот.
- **«⚠️ Проблемные заявки»** — посмотреть ошибки. Подписки ограничивают уведомления, доступ к заявкам других филиалов сохраняется.

Первоначальные администраторы задаются в `ADMIN_TELEGRAM_IDS` через запятую. `ADMIN_TELEGRAM_ID` остаётся совместимым необязательным ID владельца; если пусто, владелец для диагностики — первый ID CSV. Добавленные в меню роли, имена и подписки хранятся в SQLite. Всем администраторам нужно написать `/start`, чтобы Telegram разрешил отправку уведомлений.

## Обновление работающего Mac Mini

Не импортируйте старую локальную SQLite-копию поверх серверной: новые заявки и роли уже находятся на сервере. Сохраните серверный volume и его резервную копию.

На текущем компьютере готовый образ расположен в `outputs/itishkino-promobot-0.3.1-linux-amd64.tar.gz`. Создайте `transfer` на сервере и отправьте архив вместе с `outputs/SHA256SUMS`. Если подключение идёт через локальный SOCKS Tailscale на 1055:

```sh
ssh -o 'ProxyCommand=nc -X 5 -x 127.0.0.1:1055 %h %p' root@100.116.241.99 'mkdir -p /root/tg-bots/itishkino-promobot/transfer'
scp -o 'ProxyCommand=nc -X 5 -x 127.0.0.1:1055 %h %p' \
  outputs/itishkino-promobot-0.3.1-linux-amd64.tar.gz outputs/SHA256SUMS \
  root@100.116.241.99:/root/tg-bots/itishkino-promobot/transfer/
```

При другом способе SSH используйте тот же маршрут/ProxyCommand, через который уже подключились. Секреты и конфигурация VPN в образ не включены.

Дальше на Mac Mini, из существующего каталога проекта:

```sh
cd /root/tg-bots/itishkino-promobot
# Сначала останавливаем старую версию и создаём backup старым образом.
docker compose -f compose.yaml -f compose.vpn.yaml stop bot
docker compose -f compose.yaml -f compose.vpn.yaml run --rm bot backup
git pull --ff-only
(cd transfer && sha256sum -c SHA256SUMS)
docker load -i transfer/itishkino-promobot-0.3.1-linux-amd64.tar.gz
```

Обновите рабочие runtime-файлы скриптом ниже. Вместо `ID_IT` впишите числовой ID IT-аккаунта. Скрипт сохранит владельца и остальных администраторов, которые уже находятся в ENV/старом JSON, добавит указанный ID, добавит четыре филиала. Токен, CRM email/API-ключ, proxy, старые промоутеры и настройки текущего филиала сохраняются. Резервные копии JSON/ENV создаются в том же закрытом каталоге. База и VPN-конфигурация этим скриптом не изменяются.

```sh
python3 scripts/upgrade-franchise.py --runtime runtime --admin-id ID_IT --dry-run
python3 scripts/upgrade-franchise.py --runtime runtime --admin-id ID_IT
```

Если используете `PROMOBOT_RUNTIME_DIR`, замените `--runtime runtime` на фактический закрытый каталог. Скрипт предназначен для этой CRM с текущей Преображенкой (4), воронкой (1) и источником (6); при несовпадении отказывается менять файлы. Для нового запуска с нуля используйте `config/franchise.example.json` и `.env.example`.

Проверки и запуск:

```sh
docker compose -f compose.yaml -f compose.vpn.yaml run --rm bot branch-check
docker compose -f compose.yaml -f compose.vpn.yaml run --rm bot network-check
docker compose -f compose.yaml -f compose.vpn.yaml up -d --no-build bot
docker compose -f compose.yaml -f compose.vpn.yaml logs --tail=50 bot
```

`branch-check` не создаёт лидов, не отправляет Telegram-сообщений, не выводит контакты/ключи. `network-check` должен показать `crm: ok`, `telegram: ok`, `webhook_present: false`. VPN используется уже настроенный; менять его образ и ключи для этого обновления не требуется.

При первом открытии базы миграция 5 добавляет новые таблицы и поля. Прежние черновики, заявки, очередь, роли и DB identity сохраняются. Перед миграцией дополнительно создаётся `before-migration-5.sqlite3`. Локальная копия бота должна оставаться остановленной; один токен обслуживается одним polling-процессом.

После запуска отправьте `/start` и выберите подписки. Проверка вдвоём: первый промоутер создаёт заявку в Преображенке, второй — в Кузьминках; проверьте филиалы карточек CRM, имена промоутеров в меню и личные подписки администраторов. Не вводите вымышленные заявки в рабочую CRM без намерения сохранить их там.

## Формат CRM в 0.3.1

Примечание новой заявки содержит только дату и время подтверждения по Москве без секунд и следующей строкой «писать», «звонить» или «писать/звонить». Например:

```text
06.10.2026 18:04
писать/звонить
```

Исходный комментарий, полные данные семьи, контакты и мессенджеры находятся в одной коммуникации. Метки с ID заявки в ней нет; ID остаётся только в `custom_promo_request_id`. Даже при пропуске свободного комментария создаётся одна коммуникация с данными семьи.

Перед созданием коммуникации бот сохраняет список уже существующих коммуникаций и фазу операции в SQLite. После ответа API сохраняет конкретный communication ID. При потерянном ответе ищет точное новое совпадение вне сохранённого списка с нужным автором и типом; отсутствие/неоднозначность требуют проверки вместо повторного создания. Незавершённые заявки старого формата сохраняют первоначальный payload, чтобы проверка уже выполненной записи после обновления не давала ложное расхождение.

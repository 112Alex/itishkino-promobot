# Alfa CRM: факты и реальная приёмка

## Что известно из официальных источников

[REST API](https://alfacrm.pro/usefull/integrations/integration/api) описывает JSON POST, авторизацию `/v2api/auth/login`, заголовок `X-ALFACRM-TOKEN`, пагинацию `page/items/count/total`, ответы записи `success/errors/model`. Документированный потолок — 5 запросов/сек; бот использует равномерно 4/сек, включая login и сверку. Токен кешируется, 401 допускает один refresh; 403 не зацикливается.

Поля Customer включают `name`/`legal_name` с лимитом 50, `branch_ids`, `lead_status_ids`, `lead_source_id`, `phone`, `web`, `note`, `assigned_id`, `teacher_ids` и `custom_*`. Для чтения нужны лиды и клиенты (`is_study=2`), активные и архивные (`removed=1`). Для комментария описаны филиальные `communication/index` и `communication/create` с `class=Customer&related_id=ID`. Pipeline/custom metadata в общем описании не дают достаточного контракта: выясняются в конкретной CRM, автоматически не угадываются.

[Практическая схема интеграции](https://alfacrm.pro/usefull/knowledge/rekomendacii-po-rabote-s-sistemoj/v2api-prakticheskaya-skhema-integracii) и [настройки дополнительных полей](https://alfacrm.pro/usefull/knowledge/main-sections/settings) — дополнительные первичные источники для владельца. Примеры документации не подтверждают автоматические действия и права именно вашего пользователя.

## Что ещё неизвестно

| Значение | Где проверить |
|---|---|
| Числовой ID «Айтишкино — Преображенка» | branch/index; точное имя |
| ID «Основной» воронки, связь с её этапом | pipeline/index если доступен, lead-status/index, настройки CRM |
| ID «Не разобрано» | выбранный этап в нужной воронке |
| Источник и его точное имя | только чтение карточки 887 + lead-source/index |
| Системное имя «ID заявки промобота» | custom-кандидаты из 887 сопоставить с настройками поля |
| ID технического пользователя | профиль/справочник пользователей, проверка автора комментария |
| phone/web, архивная видимость и дополнительные места Telegram-контактов | реальные ответы и контрольные старые карточки |
| Формат «без ответственного» | тестовая запись и чтение результата |
| Разметка note, комментария, автор | реальный интерфейс CRM |

Для нового подключения эти значения остаются неподтверждёнными. Результаты текущего подключения см. в [акте приёмки](crm-acceptance.md). Значение custom-поля карточки 887 не используется как наш request ID. Карточка 887 никогда не изменяется и не удаляется приложением.

## Read-only bootstrap

В защищённом локальном env укажите режим real, email/key, адрес CRM; в отдельном JSON оставьте неподтверждённые флаги false. `bootstrap` не требует разрешения записи и не вызывает create/update/delete:

```sh
.venv/bin/promobot --env /etc/promobot/test-real.env bootstrap
```

Сначала получает список филиалов. Впишите установленный `crm_id` в JSON и повторите для филиальных справочников/карточки 887. При отключённом основном филиале документация требует branch-scoped branch/index: в этом случае подтвердите известный активный branch ID в интерфейсе; адаптер/команду bootstrap нужно согласовать с этим ответом, не угадывать. Отчёт содержит только названия/ID справочников, source/status IDs карточки, имена custom-кандидатов и типы контактов. Значения полей, телефоны и комментарий карточки не печатаются. Если невозможно сопоставить custom-поле по ключам, откройте настройки или уточните у поддержки CRM.

Если pipeline/index недоступен, это записывается как неизвестный метод; бот не создаёт воронку. Перед первым включением реальных записей владелец проверяет, что `status_id` относится к `pipeline_id` с нужным именем. Для текущей CRM подтверждён начальный этап: `pipeline_id=1`, поле этапа при создании пропущено; чтение возвращает `lead_status_id=null`. Конфигурация `initial_unassigned=true`, `status_id=null` включает этот проверенный вариант. Остальные конфигурации используют прежнее `lead_status_ids`.

Проверьте чтением известные активный лид, клиента и архивные карточки; поиск обязан видеть все их контакты. Бот обходит **все страницы** с проверкой счётчиков, ID и филиала. Username сравнивается в `web` без регистра; телефон — во всех элементах `phone`. Если ваша CRM хранит Telegram иначе, `contacts_verified` остаётся false до доработки адаптера. Неподдерживаемый phone-формат блокирует создание, а не считается отсутствием совпадений. Старый номер с однозначной записью и допустимой длиной нормализуется в E.164 даже при невалидном диапазоне в справочнике номеров: его ключ участвует в поиске дублей. Это отличается от ввода новой анкеты, где остаётся строгая проверка номера. Телефоны с несколькими номерами в строке, добавочными, слишком короткой длиной или неподдерживаемой структурой требуют проверки администратора. Контактный кеш для разрешения записей не используется.

## Разрешение реального контракта

В отдельной тестовой среде CRM/проверяемой вручную API-записи владельца установите ожидаемый контракт: точные ID, строковое request-поле, технического пользователя, запись и чтение note/phone/web, `assigned_id=null`, `teacher_ids=[]`, создание комментария `{type_id:1,comment:...,user_id:technical_user_id}` с автором технического пользователя. Если CRM требует другой способ, адаптер меняется по фактическому ответу; не устанавливайте true поверх несовместимого контракта. До этого реальный запуск бота закрыт. ID 887 не участвует в этих записях.

После этой проверки заполните `verified_contract`, `archive_visibility_verified`, `contacts_verified`, `unassigned_verified`, `communication_verified`. Флаги — запись результатов проверки владельцем, а не автоматическое доказательство. Адаптер повторно сверяет каждую созданную карточку и коммуникацию перед delivered; расхождения уходят в manual_review.

## Явный интеграционный тест

Команда не запускается pytest/обычным run. Используйте **ENVIRONMENT=test**, **CRM_MODE=real**, отдельную БД приёмки, проверенный контракт и тестового технического пользователя:

```sh
.venv/bin/promobot --env /etc/promobot/test-real.env integration-test --allow-real-write
```

Она проходит анкету через тот же сервис, создаёт одну вымышленную семейную заявку с уникальным тестовым username без фиктивного телефона, доставляет через обычный worker и печатает только номер/статус/CRM ID. Не отправляет Telegram-outbox. Учтите, что это **реальная запись** в указанной CRM: тестовые права/ветка и ручной просмотр нужны заранее. Автоматическое удаление не предусмотрено. Отклонение CRM и повторная попытка не создают произвольные новые данные при обычном запуске.

Ручная приёмка после команды:

1. В интерфейсе найдите тестовую карточку по request ID. Воронка «Основная», этап «Не разобрано», точный существующий источник, нужный филиал, ответственный/педагоги отсутствуют. Нет dob, пола, групп, занятий и второй карточки ребёнка.
2. Note начинается с условий связи, затем исходный комментарий, полный состав семьи и номер/время подтверждения по Москве. В воронке полезное примечание видно. В «Коммуникациях» одна запись с тем же комментарием и меткой request ID; автор — технический пользователь.
3. Проверьте отдельной анкетой телефон с несколькими мессенджерами, международный номер, только username и отсутствие комментария. Записей коммуникации для пропуска быть не должно.
4. Повторите **тот же контакт** через тестового Telegram-бота: новая локальная заявка duplicate_review, существующая CRM-карточка неизменна. Проверьте совпадения со старыми лидами, клиентами и архивом без request ID. Владелец получает уведомление, промоутер не видит чужие детали.
5. Приостановите доступ к CRM: анкета и «Заявка сохранена» работают, задача ожидает; после восстановления сверяется результат. Перезапустите службу после подтверждения. Не симулируйте неизвестный create вручную редактированием БД в рабочем режиме.
6. Отключите VPN: входящие/уведомления Telegram недоступны; ранее сохранённые задачи CRM могут продолжить работать напрямую. После включения VPN outbox возобновляется. Проверьте перезагрузку DietPi и отсутствие второго polling.
7. Запишите результаты в локальный акт приёмки: дата, версии, проверенные IDs/форматы/автор, непроверенные пункты. Никаких секретов или контактов в отчёт.

## Остаточные ограничения

Поиск + создание — две внешние операции. API не подтвердил уникальность custom-поля или серверный idempotency key. Локальный единственный worker и claims защищают от двух промоутеров этого бота; менеджер может создать карточку в промежутке. Такое окно контролируется организационно/последующей сверкой, а не объявляется устранённым.

После неопределённого write выполняются ограниченные чтения. Если карточка/комментарий не найден достоверно, manual_review; слепого повторного create нет. Локальный CRM ID с исчезнувшей/невидимой карточкой тоже блокирует создание. Автоматическое исправление уже подтверждённых заявок и принудительный обход дублей не реализованы.
